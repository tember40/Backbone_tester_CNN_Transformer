18.1

모델 이름을 고르기 전에

18.1 무엇을 비교하려는가?

먼저 작업이 CIFAR-10의 10종 이미지 분류인지, 사용할 장비와 시간은 얼마인지, 목표가 실행 이해인지 충분히 학습한 성능 비교인지 적습니다. 이 저장소는 분류 프레임워크이며 모델 이름이 같아도 논문의 입력 크기·헤드·학습 recipe와 다를 수 있습니다.

기록할 조건구체적으로 적을 것
데이터분할 seed, validation 비율, 각 split의 실제 표본 수, 전처리
모델·학습model ID, 초기화·사전학습 여부, epoch, batch, learning rate, optimizer
선택 기준어떤 validation 지표로 checkpoint와 설정을 선택하는가?
자원·환경장비·dtype·소프트웨어 버전, 시간·메모리 제약, 측정 범위

처음에는 perceptron이나 작은 MLP로 전체 경로를 확인하고, 이미지 구조를 쓰는 CNN을 다음 기준으로 둘 수 있습니다. 이는 비교를 좁히는 순서이지 작은 모델이 항상 빨리 수렴하거나 최종 성능이 충분하다는 보장은 아닙니다. 같은 recipe의 비교와 모델별 조정 비교도 구분하세요.

18.2

실행 확인과 결과 파일

18.2 작게 실행하고 무엇을 볼까?

프로젝트 폴더에서 설치를 마친 뒤 아래 명령으로 환경과 모델 목록을 먼저 확인합니다. PowerShell 활성화가 막혔어도 .venv\Scripts\python.exe를 직접 실행할 수 있습니다. macOS·Linux에서는 해당 경로를 .venv/bin/python으로 바꿉니다.

.\.venv\Scripts\python.exe -m cifar10_lab doctor
.\.venv\Scripts\python.exe -m cifar10_lab list-models
.\.venv\Scripts\python.exe -m cifar10_lab train --model perceptron --quick --device cpu --num-workers 0 --save-plots

첫 실행은 CIFAR-10 다운로드가 필요할 수 있습니다. --quick의 기본은 1 epoch, train 최대2,048·validation 최대512·test 최대512개입니다. 실제 수는 로그와 설정으로 확인하세요. CPU에서 실행 가능해도 다운로드 시간과 장비별 학습 시간은 다릅니다. 이 단계는 충분한 정확도를 얻는 절차가 아닙니다.

출력의 Run ID, 데이터·체크포인트 경로, Result saved to, Plot saved to를 확인합니다. 저장 PNG에는 학습/검증 곡선과 혼동행렬·클래스별 결과가 있습니다. 체크포인트가 이미 있으면 학습을 건너뛸 수 있으므로 이번 실행에서 실제로 훈련했는지도 확인하세요. 이어 학습은 --resume --epochs 5처럼 전체 완료 epoch 목표를 주며, 새 학습은 별도 출력 경로와 --retrain의 덮어쓰기 범위를 확인한 뒤 실행합니다.

18.3

답을 보고 고르지 않기

18.3 학습·선택·최종 평가를 나누자

  1. Train: 가중치 갱신에 사용합니다.
  2. Validation: epoch·설정·모델 선택에 사용합니다.
  3. Test: 선택을 마친 뒤 최종 결과를 보고하는 별도 자료입니다.

data.py는 공식 train split을 seed로 섞어 train/validation으로 나누고, test는 공식 test split에서 가져옵니다. 학습에는 RandomCrop·HorizontalFlip을 적용하지만 validation/test에는 적용하지 않고 같은 정규화 상수를 사용합니다. engine.py는 validation accuracy가 가장 높은 epoch의 가중치를 보관하고 학습 종료 뒤 그 상태를 불러옵니다. 동률이면 먼저 나온 epoch를 유지합니다.

주의할 점이 있습니다. 현재 CLI의 train은 학습 뒤 test를 평가하고, compare도 test accuracy로 보고서를 정렬합니다. 따라서 보고서를 여러 번 보며 설정을 고르면 test가 사실상 validation 역할을 하게 됩니다. 실행 확인과 최종 성능 선택을 분리하고, 모델 선택은 validation 기록으로 하세요. 최종 비교에서는 test를 보고 바꾼 설정과 횟수를 숨기지 않습니다.

Data leakage는 최종 평가에 남겨야 할 정보가 학습·선택에 들어가는 문제입니다. 같은 원본의 중복·유사 이미지가 split을 가로지르는지, 새 데이터에서 평균·표준편차를 전체 split으로 미리 계산하지 않았는지 확인하세요. 일반적인 전처리 불일치·누수 원리는 공식 점검 문서도 참고할 수 있습니다. 이 프로젝트의 고정 정규화 상수를 현재 실행에서 test로 새로 맞추는 것은 아닙니다.

Train만 계속 좋아지고 validation이 악화되면 overfitting을 의심할 수 있습니다. 하지만 데이터 분포·전처리 차이도 확인해야 합니다. 둘 다 나쁘면 underfitting뿐 아니라 학습률·라벨·gradient 경로 문제도 후보입니다. 진동에는 큰 학습률, 작은 배치, 데이터·수치 문제가 모두 관련될 수 있으므로 원인을 하나로 확정하지 마세요.

이 저장소의 train 지표는 증강과 train 모드에서 가중치를 갱신하는 동안 집계하고, validation은 epoch 끝의 고정 가중치·eval 모드로 계산합니다. 따라서 두 곡선은 조건이 완전히 같지 않고, train loss가 validation loss보다 큰 것만으로 오류라고 할 수 없습니다. 필요하면 같은 eval 전처리·모드로 train 일부를 별도 평가하여 비교하세요.

또한 loss는 확신의 정도에 반응하고 accuracy는 argmax의 정오답만 셉니다. 둘이 같은 epoch에서 최선일 필요는 없습니다. 현재 checkpoint 선택 기준은 최소 validation loss가 아니라 최대 validation accuracy라는 점을 곡선과 함께 확인하세요.

18.5

실습 18.2 · 평균 뒤의 클래스

18.5 정확도 90%가 숨기는 것

Confusion matrix의 행은 정답, 열은 예측입니다. 대각선은 정답 수이고, 행의 합은 그 클래스의 실제 표본 수인 support입니다. 예를 들어 정답 A가 B로 분류된 건수는 [A,B]입니다. 이 축 관례와 프로젝트의 confusion_matrix[label,prediction]가 일치합니다.

행: 정답 · 열: 예측 · 숫자는 표본 수
정답＼예측ABC

전체 accuracy = 대각선 합 ÷ 전체 표본 수클래스 recall = 해당 대각선 ÷ 해당 행의 합

첫 예는 (8+7+7)/30≈73.33%입니다. 두 번째는 90/100=90%지만 B·C의 recall은0%입니다. 클래스 recall을 같은 비중으로 평균하면 약33.33%가 되어 다수 클래스에만 의존하는 결과를 구분할 수 있습니다. 이 불균형 예시는 실제 CIFAR-10 전체의 클래스 비율을 나타낸 것이 아닙니다.

프로젝트의 per_class_accuracy는 행 기준 recall이며 precision이 아닙니다. 평가 표본이 없는 클래스는 코드에서0을 반환하지만, 틀린 표본이 있었다는 뜻이 아니라 평가 근거가 없다는 뜻입니다. 이 실습은 그 경우 N/A로 표시하고, 평균에서도 제외했다고 명시합니다. 실제 결과를 읽을 때도 support를 함께 확인하세요.

18.6

숫자에서 표본으로

18.6 오분류를 보고 무엇을 확인할까?

혼동이 큰 행·열을 고르고 해당 정답/예측의 표본을 모아 봅니다. 배경·작은 물체·가림·애매한 정답·전처리 잘림 등 가능한 원인을 적고, 맞힌 표본도 같은 기준으로 함께 봅니다. 잘못된 사례 몇 개만 골라 “이 모델은 배경만 본다”고 단정하지 마세요.

evaluate_model_detailed는 labels와 predictions를 같은 순서로 반환하지만, 저장 JSON에는 기본적으로 그 표본별 배열이나 원본 이미지가 없습니다. 반환 배열은 dataloader가 낸 순서와 대응시켜야 하며, subset·shuffle 때문에 원본 dataset index와 같다고 가정하면 안 됩니다. testloader의 평가 순서를 유지하고 필요한 이미지 배치를 함께 모아 확인하세요.

main.ipynb의 데이터 미리보기·평가 흐름과 연결할 때는 이미지를 표시하기 위해 정규화를 되돌리는 것과, 모델 입력 전처리를 바꾸는 것을 구분합니다. 여기서는 검증하지 않은 Grad-CAM이나 Attention 지도를 새로 만들어 원인 설명으로 제시하지 않습니다.

18.7

실제 평가 경로

18.7 eval과 no_grad는 같은 설정일까?

cifar10_lab/engine.py · 평가 경로 발췌
model.eval()
with torch.no_grad():
    outputs = _main_logits(model(images))
    predictions = outputs.argmax(dim=1)
    correct += (predictions == labels).sum().item()
confusion_matrix[label.long(), prediction.long()] += 1
class_totals = confusion_matrix.sum(dim=1)
class_correct = confusion_matrix.diag()

반복문·장치 이동·반환 부분을 생략한 코드이며 그대로 독립 실행하는 블록은 아닙니다. eval()은 Dropout·BatchNorm 등의 모드를 바꾸지만 미분 기록을 끄지는 않습니다. 반대로 no_grad()만 사용해도 train 모드의 Dropout이나 BatchNorm 통계 갱신이 자동으로 멈추지 않습니다.

학습의 CrossEntropyLoss에는 정답 클래스와 원래 logits를 넣습니다. 먼저 softmax한 값을 다시 입력하는 것은 이 프로젝트의 경로와 다릅니다. 균등한 10클래스 확률의 손실은 −ln(0.1)≈2.3026이지만, 학습 초기 loss가 반드시 이 값이어야 하는 것은 아닙니다. 초기 logits의 크기나 불균등한 예측을 함께 확인해야 합니다.

18.8

다시 실행할 때의 조건

18.8 seed 하나와 숫자 하나를 넘어서

같은 seed는 분할·초기화 등 무작위 요소를 통제하는 출발점입니다. PyTorch 재현성 안내처럼 다른 버전·장비·CPU/GPU에서 완전히 같은 결과가 보장되지는 않습니다. --deterministic의 사용 여부, 버전과 장비를 남기고 여러 seed의 평균·변동을 함께 보고하세요. 서로 다른 모델이 같은 분할 seed를 쓰더라도 파라미터 개수와 난수 소비 순서까지 같다는 뜻은 아닙니다.

OOM이면 먼저 배치 크기와 해당 연산의 입력 크기를 확인합니다. 배치를 줄이면 optimizer 갱신 횟수·BatchNorm 통계 등 학습 조건도 바뀔 수 있으므로 성능 비교 기록에 남겨야 합니다. 파라미터 수가 작다는 이유만으로 학습 메모리가 반드시 작다고 단정하지 않습니다.

보고서의 inference_ms_per_image는 warm-up 뒤 최대5개 배치의 forward 시간/이미지 수이며 데이터 읽기·장치 전송은 제외합니다. warm-up 뒤 배치가 없으면0을 반환하므로 0ms를 무한히 빠른 모델의 측정값으로 해석하면 안 됩니다. GPU 시간에는 동기화가 들어갑니다. 지연시간은 다른 장비·배치와 직접 비교하지 마세요.

checkpoint_size_mb는 이름과 달리 1024²로 나눈 MiB이며, 저장된 optimizer·마지막 상태·최적 상태·기록을 포함한 파일 크기입니다. 순수 파라미터 용량이나 실행 중 최대 메모리와 다릅니다. 실험 JSON·checkpoint·환경 정보를 묶어 보존하고, 기존 결과를 덮어쓰기 전에 출력 경로를 확인합니다.

18.9 다음 실행의 가설을 정하자

관찰가설 → 확인 → 다음 조치
두 split 모두 나쁨학습 자체 문제? → 소수 train 표본의 입력·라벨·gradient와 loss 감소 확인 → 정상 경로를 확보한 뒤 규모 조절
train만 개선과적합 또는 평가 조건 차이? → 같은 eval 조건과 split·누수 점검 → 필요한 정규화·증강을 한 가지씩 비교
특정 클래스만 나쁨표본·라벨·배경 차이? → support와 오분류/정분류를 함께 검사 → 데이터 문제를 먼저 수정
실행마다 큰 차이무작위성·캐시 재사용·환경 차이? → seed·Run ID·trained_this_run·버전 비교 → 조건을 고정한 반복

소수 표본에 맞추는 검사는 데이터 파이프라인과 최적화가 동작하는지 보는 진단이지 일반화 성능 증명이 아닙니다. 결과를 본 뒤 “모델이 안 좋다”로 끝내지 말고, 다음 실행에서 바꿀 변수 하나와 유지할 조건을 적으세요.

비교 명령은 cifar10-lab compare --models perceptron mlp resnet18 --quick처럼 실행할 수 있습니다. 단, 이는 세 모델이 같은 짧은 설정으로 실행되는지 보는 예입니다. 실제 선택은 18.3절의 validation 기준과 자원 제약으로 진행합니다. 결과가 가설을 지지하지 않으면 그 사실도 기록합니다.

  • 곡선은 원인을 확정하는 답이 아니라 확인할 가설의 출발점입니다.
  • 전체 정확도에 클래스 support·recall·오분류를 연결합니다.
  • 모드·전처리·재현성·캐시·측정 조건을 모델 구조와 분리해 점검합니다.
Q1. 검증 손실 최저 epoch가 저장 epoch와 다른 이유는?

현재 구현은 validation accuracy의 최댓값으로 선택합니다. loss와 accuracy는 서로 다른 지표이므로 최적 epoch가 다를 수 있습니다.

Q2. 클래스 C의 support=0, 코드 결과=0%이면?

C의 평가 표본이 없으므로 실패율을 판단할 수 없습니다. support와 함께 N/A로 해석하고, 평균을 어떻게 계산했는지 명시합니다.

Q3. 다음 실행에서 꼭 적을 네 가지는?

관찰한 사실, 가능한 가설, 확인하기 위해 바꿀 변수, 그대로 유지할 조건입니다. 결과와 가설의 지지 여부도 실행 후 남깁니다.
